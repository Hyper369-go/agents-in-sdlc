プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりしたプロセスが必要です。GitHub Copilot アプリは組織の既存の開発フローに沿って、適切な方法で適切なものを作れるよう支援します。このレッスンから数回にわたり、一般的なエージェント駆動の開発プロセスに沿って、新機能を Issue から作成し、コードの妥当性と機能の動作を確認し、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能開発を続ける間は、同じセッションを使います。通常はファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため、手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能開発を続ける中で、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリや発行元でゲームを絞り込む必要があります。バックログの Issue には機能の説明がありますが、カテゴリを組み合わせる方法などは、コードを書く前に合意する必要があります。Plan モードで決定し、範囲を明確にした実装を Autopilot に任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本が変わるわけではありません。むしろ、基本がさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 実装内容を記載した Issue を開きます。
2. 作成するものの計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合はここに示した流れを調整したものです。

この標準的な進め方に従えば、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューを受けるようにできます。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを決めます。プロンプト欄の下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと共同で作業します。エージェントは変更を提案し、続行する前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行に進む前に、計画をレビューして承認します。
- **Autopilot**: エージェントがコードを書き、テストを実行して、入力を待たずに作業を繰り返します。

最初に Plan モードで計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** の下にある Tailspin Toys リポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選びます。**Allow users to filter games by category and publisher** を開きます。テンプレートに登録済みの Issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づいて **new working tree** を選びます。

   ![GitHub Copilot アプリの Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. セッションに Issue が添付されていることを確認し、モード選択から **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションから実行できない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前に進め方をレビューできます。Issue からセッションを始めたため、機能の要望はすでにコンテキストに含まれています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発行元のフィルタリング、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方法や、該当するゲームがない場合の動作など、不明な点について合意します。

計画には、プロジェクト既存のツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。ここではフィルター機能の実装とテストに集中し、品質ワークフローの後に PR を作成します。承認する前に計画を修正し、後で検証できるよう Issue の URL と合意事項を控えます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan** または使用中のバージョンで同等の選択肢を選びます。承認によってモードが自動的に切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を始めます。合意した計画に沿って作業を進め、コードを生成してテストを実行する様子を確認できます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると Copilot が報告した場合は、チェック完了と判断する前にセットアップの問題を解決してください。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

他のコードと同様に、生成されたコードもマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 変更を Issue と承認済みの決定に照らし合わせます。複数カテゴリや発行元の組み合わせも確認し、リポジトリの既存指示に従っていることを確かめます。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。チェックのスキップは成功ではありません。
4. 問題を解決し、影響を受けるチェックを再実行してから実装を受け入れます。Playwright の E2E 設定はビルド済みのプレビューを起動し、ローカルサーバーを再利用することがあります。テスト対象が前のレッスンのサーバーではなく、このワークツリーのサーバーであることを確認してください。

## 新しい機能を試す

コードがよさそうでも、実際に動くでしょうか。前回と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで、アプリの起動とブラウザーキャンバスでのページ表示を Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot アプリ内にブラウザーが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターをクリアしてから発行元を選び、結果がその発行元に一致することを確認します。
4. カテゴリと発行元のフィルターを組み合わせ、Issue と承認済みの計画に照らし合わせます。複数カテゴリがサポートされている場合は、合意した組み合わせの動作を確認します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットし、すべてのゲームが再表示されることを確認します。
6. 確認が終わったら、次のプロンプトでこのセッション用に起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに備えてセッションを保持する

まだフィルター機能の PR を作成したりマージしたりしないでください。レッスン 4 から 8 まで、同じセッション、ワークツリー、ブランチを使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしておいてください。次のレッスンで同じセッションに戻ります。
